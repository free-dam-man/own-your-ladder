# 节点方法论全教程：从勘察到订阅，一条自己的线是怎么长出来的

> 本文只讲方法，不发任何现成订阅、不给任何真实地址。文中所有需要填入你自己信息的位置，都用 `<你的…>` 占位。方法可复刻，参数靠自备。

---

## 0. 先说清这套方法解决什么问题

自建节点最大的成本不是钱，是试错：平台太多、规则太杂、今天能用的明天失效。单个平台逐个研究，学费交不完。

这套方法的核心是把试错外包给流程：

- **勘察**由大模型 agent 批量做；
- **部署**用统一模板做；
- **验收**用拨测做，不靠面板显示、不靠感觉；
- **交付**用聚合订阅做，一条线进客户端，死活自动管理。

下面按顺序展开。

---

## 1. 方法论主线：五步流水线

### 1.1 勘察：先建一张平台表

让 agent（或你自己）对候选平台逐个核查四件事，记成表：

| 核查项 | 看什么 |
|---|---|
| 免费额度 | 有没有免费层/赠送额度，额度按什么计（时长、流量、调用次数） |
| 注册门槛 | 是否必须绑卡、是否要实名、是否对注册地区有限制 |
| 部署形态 | 给的是虚拟机、容器、函数还是边缘运行时，决定了能跑什么服务 |
| 区域 | 可选区域有哪些，是否能自选 |

勘察的结论不是「哪个平台最好」，而是「哪个平台现在可用」。平台状态变化很快，这张表要定期重跑——这正是适合交给 agent 的活：重复、量大、标准明确。

### 1.2 部署：统一模板，变量最小化

不管落点是哪个平台，部署时坚持三统一：

1. **服务统一**：都部署同一类代理服务（如 xray 类），配置结构一致；
2. **出参统一**：每条线最终都产出同一种格式的节点信息（协议、地址、端口、密钥字段齐全）；
3. **命名统一**：节点名 = 地区 + 平台简称 + 序号，例如 `<地区>-<平台>-01`，日后聚合、排障都靠它。

模板化的意义：新平台接入时，你改的只有「怎么把模板塞进去」，不用重新设计整条线。

### 1.3 拨测：唯一验收标准

部署完成只说明「装上了」，不说明「能用」。每条线必须过三查（详见第 4 节清单）：

1. **探活**：通过该节点访问探活端点（如 generate_204 类端点），必须返回 HTTP 204；
2. **出口地区**：通过该节点查询出口 IP 的归属地，必须与预期地区一致；
3. **订阅拉取**：聚合后的订阅链接必须能被客户端真实拉取并解析。

三查全过，才算一条活线。任何一查不过，标记、隔离、找原因，不要混进订阅里凑数。

### 1.4 聚合：多条线变一条订阅

活线攒到几条之后，用聚合器统一管理：

- 把各条线的节点信息汇总成一份订阅文件；
- 按地区分组，组内按拨测延迟排序；
- 定时重跑拨测，连续失败的线自动剔除，恢复的自动加回；
- 对外只暴露一个订阅地址：`<你的聚合订阅地址>`。

这样客户端永远只订阅一个链接，后台的线怎么增减都不影响使用。

### 1.5 客户端收尾：自动测速组

把聚合订阅导入 Shadowrocket 等客户端后：

- 建一个「自动测速」策略组，包含全部节点；
- 客户端按间隔自动测速并切换到当前最快的一条；
- 个别业务需要固定地区的，再从组里单独挑线固定——那是进阶用法，先把自动组跑稳。

## 2. 一键部署家族：三套打法

### 2.1 Railway 一键仓（新手首选）

**原理**：把 xray 类服务的部署动作打包成一个代码仓库，托管平台按仓库配置自动构建、运行，并直接给出订阅输出。

**步骤**：

1. 打开公开仓库：https://github.com/free-dam-man/railway-anon-xray ，点 Fork 到 `<你的 GitHub 账号>`；
2. 在 Railway 新建项目，选择从你 fork 的仓库部署；
3. 按仓库 README 填写必要的环境变量（凡是密钥类参数，平台会生成或由你自设，**不要把任何密钥写进仓库代码**）；
4. 等待部署完成，按 README 的说明拿到 `<你的订阅地址>`；
5. 把订阅导入客户端，按第 4 节清单拨测验收。

**门槛**：一个 GitHub 账号 + 一个 Railway 账号；不需要会写代码。
**注意**：平台的免费政策和部署规则会调整，部署前先看一遍仓库 README 的最新版和平台当前条款。

### 2.2 Cloudflare Worker + KV 模式（免维护之选）

**原理**：不租服务器，直接借边缘网络的运行时执行代理逻辑；节点参数、分组等配置存进 KV（键值存储），改配置不用重新部署代码。

**步骤（方法层）**：

1. 准备 `<你的 Cloudflare 账号>`，开通 Workers 与 KV；
2. 创建一个 KV 命名空间，用来存节点配置；
3. 部署一份边缘代理的 Worker 代码（开源社区有多个模板可参考），把 KV 绑定到 Worker；
4. 按模板说明在 KV 里写入你的配置项（地址、密钥等一律填你自己的，存在你自己的 KV 里）；
5. 用 Worker 的访问地址按模板格式拼出 `<你的订阅地址>`，导入客户端验收。

**门槛**：愿意读模板文档；不需要服务器运维。
**适用**：怕机器过期、怕维护的人。边缘节点分布广，单点失效影响小。

### 2.3 Modal 函数节点模式（额度玩家之选）

**原理**：把节点做成云函数：有请求才唤醒、闲置自动缩零（scaledown），费用只在实际运行时产生；按大区部署多个函数实例，聚合订阅统一收口。

**步骤（方法层）**：

1. 准备 `<你的 Modal 账号>`，确认免费额度与计费规则；
2. **先设月度用量上限**（见第 5 节的坑，这是顺序问题，必须在部署之前）；
3. 写一个最小函数：启动时拉起代理服务进程，对外暴露端口；
4. 按需要的地区分别部署实例，逐个拨测；
5. 把通过拨测的实例地址汇总进聚合订阅。

**门槛**：能写一点脚本、看得懂平台文档。
**适用**：手里有闲置免费额度、想把额度换成线路的人。

## 3. 大众玩法：把方法写成提示词，交给任何大模型

上面五步流水线，可以压缩成一段任务书。把下面框架里的占位符换成你的实际情况，交给任意一个能联网、能执行操作的大模型（或按它给的步骤自己动手），就能跑起来：

```
你是一名网络部署助理。请按以下四步，为我搭建一条自用代理线路，
每一步都必须给出可验证的证据，不许只报告"已完成"：


列出 <候选平台清单> 中当前可用的部署点，逐个核查：
免费额度、是否必须绑卡、可选区域、部署形态（虚拟机/容器/函数/边缘）。
输出一张对比表，并推荐 1 个首选、1 个备选，说明理由。


在首选平台上部署 xray 类代理服务，使用统一配置模板；
密钥由平台生成或我自设，不许把任何密钥发到对话之外的地方。
完成后给出节点信息：协议、地址、端口、地区标注。


通过该节点做三项验证并贴出结果：
① 访问探活端点，确认返回 HTTP 204；
② 查询出口 IP 归属地，确认与预期地区一致；
③ 生成订阅链接并实际拉取一次，确认能解析出节点。
任何一项不通过，明确报告是哪一项、什么现象，不许跳过。


输出最终订阅链接和节点命名（格式：地区-平台-序号），
并说明这条线的已知限制（额度、有效期、平台政策风险）。
```

使用说明：

- 平台清单从你知道的免费/低价平台里填，先从一个开始，跑通再加；
- 模型给出的每一步结论，都以第 4 节清单复核，不要全盘照收；
- 涉及账号注册、绑卡等动作，永远自己操作，不要把账号密码交给模型。

## 4. 拨测验证清单（打印级）

每条新线、每次订阅更新后，逐项打勾：

- [] **探活**：经该节点访问探活端点，返回 HTTP 204（不是 200，不是超时）；
- [] **出口地区**：经该节点查到的出口 IP 归属地，与节点命名中的地区一致；
- [] **订阅拉取**：客户端真实拉取订阅成功，节点列表完整、命名无乱码；
- [] **单节点直连**：逐条单独启用测试（自动测速组会掩盖单条死线）；
- [] **延迟记录**：把本次拨测延迟记入平台表，作为下次勘察的依据；
- [] **死线处理**：连续两次拨测失败的线，从订阅中剔除并标记原因。

## 5. 常见坑（都是交过学费的）

1. **平台对机房 IP 阶段性收紧。** 某些平台/目标站点会对数据中心 IP 段整体收紧：同一条线昨天好好的，今天全灭，通常不是你配置错了，而是风口变了。对策：不要连续猛重试（会加重风控），换平台、换地区，隔段时间再测。

2. **地区标注 ≠ 实际出口。** 面板和部署页写的地区，只是机器或函数所在的区；流量真实出口可能落在别处。命名、分组一律以拨测查到的出口地区为准，别信标签。

3. **自动测速会烧额度。** 客户端测速会把订阅里每条线都唤醒一遍；函数型节点按调用计费时，一轮测速就是一轮账单。先设用量上限和告警，再开自动测速。

4. **订阅能拉 ≠ 节点能用。** 订阅文件只是一个文本列表，它永远「拉取成功」。能用与否，只看逐条拨测。

5. **单线依赖。** 任何一条线都有寿命：平台改政策、免费额度取消、IP 段被封。常备至少两条不同家族的线（比如一键仓一条 + 边缘一条），一条死了日子照过。

6. **密钥进仓库。** 一键部署最容易犯的错是把密钥写进代码推上公开仓库。密钥只放平台的环境变量或你自己的配置存储里，仓库永远只放模板。
